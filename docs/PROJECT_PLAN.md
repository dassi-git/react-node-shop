# תכנון פרויקט – מערכת הזמנות לעיצובי פירות

## 1. מטרת הפרויקט

פיתוח מערכת הזמנות לעיצובי פירות, שבה לקוח בוחר מוצר/עיצוב, שולח בקשת הצעת מחיר, מנהל מאשר מחיר, והלקוח משלם רק לאחר אישור ההצעה. 
זוהי מערכת מותאמת אישית ולא חנות קלאסית עם רכישה מיידית.

---

## 2. עקרון העסקי

המודל הנכון הוא:

Order → Quote Request → Admin Quote → Customer Approval → Payment → Production / Delivery

במקום המודל הרגיל:

Add to cart → payment → order

במוצרי עיצוב אישיים, המחיר תלוי בכמות, סוג פרי, גודל, תאריך משלוח, הערות, תוספות, אזור משלוח, והכנה ייחודית.

---

## 3. תהליך עבודה מומלץ

### 3.1 תהליך לקוח
1. הלקוח בוחר מוצר/עיצוב.
2. בוחר אפשרויות:
   - סוג פרי
   - כמות
   - גודל / משקל
   - תאריך משלוח
   - אזור משלוח
   - כרטיס ברכה
   - תוספות
   - הערות מיוחדות
3. מוסיף לעגלה.
4. לוחץ על "שלח בקשת הצעת מחיר".
5. נוצרת הזמנה חדשה בסטטוס `quote_requested`.
6. המנהל רואה את הבקשה.
7. המנהל שולח הצעת מחיר.
8. הלקוח מאשר/דוחה את ההצעה.
9. אם מאשר – ממשיך לתשלום.
10. לאחר התשלום ההזמנה הופכת ל"מאושרת" ומתחיל תהליך הכנה/משלוח.

### 3.2 תהליך מנהל
1. בודק הזמנות הממתינות להצעת מחיר.
2. עובר על פרטי ההזמנה.
3. מחשב מחיר סופי.
4. קובע:
   - מחיר
   - דמי משלוח
   - מקדמה
   - תאריך אספקה
   - הערות
5. שולח הצעת מחיר.
6. מעקב אחרי תשלום ואישור.
7. מעדכן סטטוס הזמנה בהתאם להתקדמות.

## 4. סטטוסים מומלצים להזמנה

- `draft`
- `quote_requested`
- `quote_sent`
- `quote_accepted`
- `quote_rejected`
- `payment_pending`
- `paid`
- `confirmed`
- `preparing`
- `ready_for_delivery`
- `in_delivery`
- `completed`
- `cancelled`

### פירוש הסטטוסים
- `quote_requested`: הזמנה נשלחה, ממתינה להצעת מחיר
- `quote_sent`: המנהל שלח הצעת מחיר
- `quote_accepted`: לקוח אישר את ההצעה
- `payment_pending`: ממתין לתשלום
- `paid`: התשלום בוצע
- `confirmed`: ההזמנה אושרה סופית
- `preparing`: בהכנה
- `ready_for_delivery`: מוכן למשלוח
- `in_delivery`: בשילוח
- `completed`: הושלם
- `cancelled`: בוטלה

## 5. דרישות פונקציונליות

### 5.1 מוצרים
- הצגת מוצרים עם תמונות
- עד 7 תמונות לכל מוצר
- גלריית תמונות בדף המוצר עם תמונה ראשית ו-thumbnails
- קטגוריות
- תיאור מוצר
- אפשרויות התאמה אישית
- מחיר בסיסי
- מצב זמינות

### 5.1.1 אפשרויות התאמה אישית ותמחור

כל מוצר יכול לכלול רשימת אפשרויות שהמנהל מגדיר בנפרד עבור אותו מוצר. האפשרות אינה כללית לכל
החנות, משום שמגש מסוים עשוי לאפשר פירות, גדלים ותוספות שונים ממגש אחר. בקבוצת הפירות המנהל
יבחר את כל הפירות האפשריים למגש מתוך הקטלוג הגלובלי, מכל העונות; העונה רק קובעת מה מוצג
ללקוח כרגע ומה תוספת המחיר.

לכל קבוצת אפשרויות יישמרו:
- שם הקבוצה, למשל "בחירת פירות", "גודל מגש" או "תוספות"
- סוג הבחירה: `single` לבחירה יחידה או `multiple` לבחירה מרובה
- האם הבחירה חובה
- מספר בחירות מרבי ב־`multiple`
- תוספת מחיר לכל בחירה מעבר לראשונה
- סדר תצוגה
- רשימת ערכים זמינים

לכל ערך יישמרו:
- שם תצוגה בעברית
- מזהה יציב לשמירה בהזמנה
- תוספת מחיר בשקלים, שיכולה להיות גם `0`
- זמינות לבחירה
- סדר תצוגה

דוגמה להגדרת מוצר:

```json
{
  "customizationOptions": [
    {
      "name": "בחירת פירות",
      "selectionType": "multiple",
      "required": true,
      "maxSelections": 4,
      "additionalSelectionPrice": 8,
      "values": [
        { "label": "תותים", "value": "strawberries", "priceAdjustment": 0 },
        { "label": "מנגו", "value": "mango", "priceAdjustment": 15 },
        { "label": "ענבים", "value": "grapes", "priceAdjustment": 10 }
      ]
    },
    {
      "name": "גודל מגש",
      "selectionType": "single",
      "required": true,
      "values": [
        { "label": "קטן", "value": "small", "priceAdjustment": 0 },
        { "label": "בינוני", "value": "medium", "priceAdjustment": 30 },
        { "label": "גדול", "value": "large", "priceAdjustment": 60 }
      ]
    }
  ]
}
```

כללי המערכת:
- המנהל יכול להוסיף, לערוך, למחוק, לסדר ולהשבית קבוצות וערכים.
- ערך מושבת לא יוצג לבחירות חדשות, אך יישמר בהיסטוריית הזמנות קיימות.
- הקונה יראה רק ערכים פעילים ויידרש למלא קבוצות חובה.
- בקבוצת פירות מרובה ניתן לבחור עד `maxSelections`, וכל פרי מעבר לראשון מוסיף `additionalSelectionPrice`.
- המחיר המוצג לקונה הוא מחיר הבסיס בתוספת כל ההתאמות שנבחרו, כפול הכמות.
- השרת בודק מחדש שהאפשרויות שייכות למוצר ושהמחירים תואמים להגדרת המוצר; אין אמון במחיר מהדפדפן.
- בהוספה לסל ובהזמנה נשמר snapshot של שם האפשרות, הערך והתוספת, כדי ששינוי עתידי במוצר לא ישנה הזמנה קיימת.

### 5.1.2 ניהול פירות עונתיים גלובלי

המערכת תכלול קטלוג גלובלי של פירות, המנוהל פעם אחת על ידי המנהל ומשפיע על כל המוצרים באתר.
הגדרת העונתיות אינה נשמרת בנפרד בכל מגש, כדי למנוע מצב שבו אותו פרי זמין או מתומחר אחרת
במוצרים שונים ללא החלטה מרכזית.

#### מטרת המנגנון

בכל תקופה המנהל יגדיר אילו פירות זמינים בעונה, אילו זמינים אך יקרים יותר, ואילו אינם זמינים.
בעת בחירת מוצר, המשתמש יראה רק את פירות העונה שניתן להזמין באותו מועד, ובמקרה של פרי יקר
יותר יוצג לידו מחיר התוספת הספציפי לאותה עונה.

#### מודל נתונים גלובלי מוצע: `FruitSeason`

לכל רשומת עונתיות יישמרו:
- מזהה פרי יציב, למשל `mango`
- שם תצוגה, למשל "מנגו"
- תאריך התחלה ותאריך סיום של התקופה
- סטטוס: `available`, `premium` או `unavailable`
- תוספת מחיר בשקלים, ברירת מחדל `0`
- האם הרשומה פעילה
- הערת מנהל פנימית או הסבר שיוצג ללקוח
- מי עדכן ומתי

דוגמה:

```json
{
  "fruitKey": "mango",
  "displayName": "מנגו",
  "validFrom": "2026-05-01",
  "validUntil": "2026-09-30",
  "status": "premium",
  "priceAdjustment": 15,
  "active": true,
  "customerMessage": "מנגו זמין כרגע בתוספת עונתית"
}
```

#### כללי תקופה

- תאריך ההזמנה או תאריך המשלוח, לפי החלטת העסק, יקבעו איזו תקופה פעילה. ברירת המחדל המומלצת
  היא תאריך המשלוח, כדי לבדוק זמינות אמיתית ביום ההכנה.
- תקופה פעילה היא רשומה ש־`active=true` והתאריך נמצא בין `validFrom` ל־`validUntil`, כולל הגבולות.
- לא יהיו שתי רשומות פעילות חופפות לאותו `fruitKey`, אלא אם מוגדרת מדיניות עדיפות מפורשת.
- אזור הזמן העסקי יוגדר במערכת, כדי למנוע שינוי עונה בחצות לפי אזור הזמן של הדפדפן.
- ניתן להכין תקופה עתידית מראש ולהפעיל או לבטל אותה בלי לשנות מוצרים.
- כאשר אין רשומה פעילה לפרי, הוא ייחשב כלא זמין להזמנה ולא יוצג כאפשרות ברירת מחדל.

#### התנהגות לפי סטטוס

- `available`: הפרי מוצג לבחירה ללא תוספת עונתית.
- `premium`: הפרי מוצג לבחירה עם תוספת המחיר הגלובלית, למשל `+15 ₪`.
- `unavailable`: הפרי אינו ניתן לבחירה ואינו נשלח ב־payload תקין להזמנה.
- פירות שאינם מוגדרים בקטלוג הגלובלי ייחשבו לא זמינים, כדי למנוע בחירות לא מוכרות.

#### חיבור למוצר ולמשתמש

- קבוצת "בחירת פירות" במוצר תכיל `fruitKey` מפורש בכל ערך ולא רק טקסט חופשי.
- `fruitKey` בערך המוצר חייב להיות זהה ל־`fruitKey` ברשומת `FruitSeason`; שם התצוגה נקבע מהמוצר/הקטלוג ואינו משמש לקישור.
- דף המוצר יקבל מהשרת את הגדרת המוצר יחד עם סטטוס העונה הנוכחית לכל ערך פרי.
- המשתמש יראה את שם הפרי, זמינותו, תוספת המחיר והודעת העונה, באופן פרטני בתוך כל מוצר.
- אותה הגדרה גלובלית יכולה להשפיע על מוצרים שונים, גם אם לכל מוצר יש רשימת פירות שונה.
- מחיר הבסיס והתוספות הקבועות של המוצר נשארים נפרדים מתוספת העונה.
- מוצר ללא קבוצת פירות ממשיך לעבוד, אך אינו מקבל בחירות עונתיות אוטומטיות.

#### תמחור ואבטחה

מחיר יחידה יחושב כך:

`מחיר בסיס + תוספות מוצר + תוספות עונתיות פעילות + (מספר בחירות - 1) × תוספת בחירה נוספת`

השרת יחשב מחדש את התוספת לפי `fruitKey` ולפי תאריך המשלוח/ההזמנה. אין לקבל מהלקוח מחיר,
סטטוס זמינות או תאריך תקופה כמקור אמת.

בעת הוספה לסל, יצירת הזמנה ושליחת בקשת הצעת מחיר השרת יוודא:
- שהפרי קיים בקטלוג הגלובלי
- שהפרי קיים באפשרויות המוצר המסוים
- שהפרי זמין בתקופה הרלוונטית
- שהתוספת שנשלחה תואמת לתוספת הנוכחית בשרת
- שכמות הבחירות וסוג הבחירה עומדים בכללי המוצר

בסל ובהזמנה יישמר snapshot מלא: `fruitKey`, שם הפרי, סטטוס העונה, התוספת, תאריך הייחוס
והתקופה ששימשה לחישוב. שינוי עתידי בעונתיות לא ישנה הזמנה שכבר נשלחה.

#### ממשק מנהל

יוקם מסך "ניהול עונתיות" גלובלי שבו המנהל יכול:
- לראות את כל הפירות ואת הסטטוס הפעיל שלהם היום
- ליצור תקופה עתידית ולבחור תאריכי התחלה וסיום
- לסמן פרי כזמין, יקר עונתית או לא זמין
- להגדיר תוספת מחיר לכל פרי במצב `premium`
- להוסיף הודעה ללקוח והערה פנימית
- לערוך, לשכפל, לבטל או לסגור תקופה
- לראות חפיפות, תקופות שפגו ושינויים אחרונים
- לבצע preview לתאריך מסוים לפני פרסום

#### ממשק משתמש

בדף מוצר יוצגו רק פירות שהוגדרו במוצר ושזמינים בתקופה שנבחרה. ליד פרי premium יוצגו:
- תג "פרי עונתי"
- תוספת המחיר המדויקת
- המחיר המעודכן של המוצר

אם פרי שנבחר בעבר הפך ללא זמין לפני שליחת הזמנה, המשתמש יקבל הודעה ברורה ויידרש לבחור
פרי זמין אחר. אין לאפשר שליחה שקטה של בחירה שפגה.

#### מקרי קצה ובדיקות קבלה

- פרי זמין ללא תוספת מוצג בכל מוצר שמגדיר אותו.
- פרי premium מוצג בכל המוצרים עם אותה תוספת גלובלית.
- פרי לא זמין אינו ניתן לבחירה באף מוצר.
- תאריך משלוח שנמצא בתקופה עתידית משתמש בהגדרת התקופה העתידית.
- תאריך בגבול ההתחלה או הסיום נחשב בתוך התקופה.
- שתי תקופות חופפות לאותו פרי נחסמות בעת שמירה.
- ניסיון לשלוח `fruitKey` שאינו קיים או מחיר מזויף נדחה בצד השרת.
- בחירה מעבר ל־`maxSelections` נדחית גם בממשק וגם בשרת.
- המנהל יכול לשמור במוצר פירות שאינם בעונה; הם לא יוצגו ללקוח עד שתהיה להם עונה זמינה.
- שינוי עונתיות לאחר יצירת הזמנה אינו משנה את ה־snapshot של ההזמנה.
- מנהל יכול לבטל תקופה ולראות מיד את ההשפעה על כל המוצרים.
- מוצר קיים עם ערכי פרי מהמבנה הישן יומר למבנה `fruitKey` בעת שמירה מחדש במסך ניהול המוצר.

### 5.6 אישור/דחייה

### 5.7 תשלום

- עדכון סטטוס להזמנה ל-`payment_pending`, ואז ל-`paid`

## 13. החלטה עסקית חשובה

בקשת מחיר היא חלק אינטגרלי מהמודל העסקי. 
לא מומלץ לקבוע מחיר מיידי לפני בדיקה של פרטי ההזמנה, כי:
- ההזמנה מותאמת אישית
- מחיר תלוי בסטייל, כמות, תוספות, פרי ויעד
- הלקוח צריך לראות מחיר סופי לפני תשלום

לכן המודל הנכון הוא:

לקוח בוחר → שולח בקשת מחיר → מנהל מציע מחיר → לקוח מאשר → תשלום

---

## 14. מסקנה

הפרויקט צריך להיות מערכת הזמנות מותאמת אישית לעיצובי פירות, עם זרימת עבודה של הצעת מחיר לפני תשלום. 
הפוקוס העיקרי הוא על:
- עיצוב מותאם
- תהליך הזמנה שוטף
- ניהול כספי ודירוג מחיר
- אפשרות לסגירת הזמנה רק לאחר אישור מסודר

זוהי מערכת אמיתית, עסקית, וניתנת להרחבה.

## 16. סיכום קצר

הפרויקט מתאים למודל של חנות בקשת מחיר, לא לחנות רגילה. 
העבודה הראשונה היא להקים את לב הזרימה: הזמנה → הצעת מחיר → אישור → תשלום.

זהו היסוד שיביא את המערכת לרמת חנות מקצועית ומהימנה.
